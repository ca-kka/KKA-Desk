# KKA Desk architecture outline

## Product boundary
KKA Desk is a private, staff/admin-only Windows desktop application. The first implementation is WPF on modern .NET, with a service/view-model separation intended to keep business logic portable later.

## Intended layers
- **Presentation:** Accessible WPF shell, navigation, dashboard, document/PDF experience, query and queue views.
- **View models:** UI state, commands, loading/error state, and permission-aware presentation.
- **Services:** authentication/session lifecycle, due-date synchronization, document/query APIs, and diagnostics.
- **Backend:** existing Supabase Auth, Postgres/RLS, Storage, and reviewed Edge Functions where suitable.
- **Local state:** minimal preferences and a generic personal reminder queue in the current Windows user's app-data folder. It is not a client-work cache and must not contain client names, identifiers, documents, credentials, or portal responses.

## Identity and authorization
Reuse existing identities where possible. Shared credentials do not automatically provide seamless SSO. MFA/AAL and any OTP/password-change gates must be preserved. The UI is not an authorization boundary: server-side RLS and endpoint checks must enforce role and client assignment.

## Data policy
Online connection is required for client data. Display last-successful sync and stale/unavailable warnings for public due-date data. Do not fabricate metrics when data has not loaded. Keep client data out of local reminders and diagnostic logs. The personal queue stores only reminder title/category/priority/due date and audit events containing action, random item ID, and time; it does not copy titles into the audit history. Atomic writes and a per-file process lock protect updates from interruption and concurrent app windows. Explicit error states prevent damaged local data from being silently replaced.

## Distribution
Windows-first private installer. Updates notify users and require confirmation. Build artifacts should be generated by Windows CI, reviewed, and tested before distribution.

## Production safety
The repository is separate from the live website/portal repository. Do not deploy changes to production or modify Supabase schema/functions without explicit approval.


## Client and family profiles

- Reuse the existing client/family relationships and stable identifiers; do not create duplicate client records.
- The existing primary-holder account/login model remains unchanged. Family members do not receive new logins as part of KKA Desk.
- A family account groups profiles; each selected profile is the tax and document scope. Credentials, PAN/Income Tax settings, GST registrations, frequency history, jobs, files and audit references are profile-scoped.
- Never assume family members share a PAN, GSTIN, portal credentials, audit status or filing frequency. Each profile and GST registration must be validated independently.
- A family-wide batch is only a UI convenience that fans out into separate profile-scoped jobs, with per-profile destinations and independent outcomes.
- Documents must be segregated by stable family/account ID and member/profile ID. A display name is never a canonical authorization or storage key.
- The tax automation feature is admin-only and local to KKA Desk. It does not change the existing client-side portal, family login behavior, or production schema/functions.
